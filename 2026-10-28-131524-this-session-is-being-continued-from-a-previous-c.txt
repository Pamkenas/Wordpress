● Done. New stress tester at wp-control/tests/load-test.php. It uses curl_multi
  to keep many requests in flight at once and watches whether Apache, PHP or
  MySQL fall over. Like the other scripts, it refuses anything that isn't a
  local test site, and it only reads.

  Run it (from the wp-control folder):
  C:\xampp\php\php.exe tests\load-test.php --target all --concurrency 50
  --seconds 60
  - --target — agent (signed snapshot endpoint), dashboard (logged-in admin
    pages), front (client home pages), or all
  - --concurrency — how many requests run at once (default 30)
  - --seconds — how long per target (default 30)

  What it reports per target: requests/second, status breakdown
  (200/302/401/5xx), latency p50/p90/p99/max, connection failures (the real "it
  crashed" signal), and 5xx server errors. Afterwards it does a recovery check:
  is MySQL still answering, do all three sites still return a page, and are the
  debug logs still clean. The final line is green if everything stayed up, red
  if the load caused errors.

  I validated it at moderate load (all three targets), 0 errors, sites
  recovered, logs clean. To really push for a crash, raise --concurrency (e.g.
  100–200).

  One heads-up: heavy runs genuinely can crash MySQL on this machine — that's
  the point of the test, but if it happens the recovery steps are the same ones
  from last time (dump, swap in a fresh data folder from mysql\backup,
  reimport). I noted that in the script header and the README.

  Two bugs I found and fixed while building it:
  - The dashboard phase first returned all 302 (not logged in). Cause: curl only
    writes its cookie jar file on curl_close, which never ran, so the jar was
    empty — plus WordPress auth cookies are HttpOnly. I switched to capturing
    the Set-Cookie headers from the login response and resending them, which
    works under concurrency.

  I also noted the new test in the README (wp-control/README.md). Nothing is
  committed.
